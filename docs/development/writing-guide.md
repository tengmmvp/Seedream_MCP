# 文档写作规范

| 项           | 值                                                                               |
| ------------ | -------------------------------------------------------------------------------- |
| **版本**     | v1.0                                                                             |
| **适用范围** | 架构方案、设计文档、规范性文档                                                   |
| **参照**     | [Apple Style Guide](https://support.apple.com/guide/applestyleguide/welcome/web) |
| **分工**     | 代码风格归 pyguide.md，仓库布局归 repo-layout.md，文档写作归本文档               |

动笔前按第 3 节定结构，行文时守第 2、4、5 节条款，交付前按第 6 节自查。第 1 节的三条原则是全部条款的裁决依据——条款未覆盖的场合，按原则推断。

## 1 写作基础

**清晰**：为读者写，不为自己写。目标读者第一次阅读就懂，不需要复读，不需要先了解作者的思路。

**一致**：同一概念全篇只用一个名字；同类条目用同一种写法。读者见到同一形态，即知是同一类信息。

**简洁**：删去一切不承载信息的词。简洁是去掉多余，不是省略必要。

冲突裁决：清晰优先于简洁；一致不因简洁让步；一致伤害清晰时，全局修正术语，不在个别处破例。

## 2 语言风格

**直接陈述**。主动语态、动词开头；描述系统行为一律用现在时——「服务器返回错误」，不是「服务器将会返回错误」。

**一句一事**。每句话只承载一个论点；一句话说不完的，拆成两句。

**意图先行**。篇的首句说这篇文档为什么存在；章的首句说本章讲什么；条目的首句说这条规则管什么。读者只读首句，就能决定要不要细读。

**用具体词**。「若干」「相关」「适当的」一类模糊词，换成具体内容，或删去。

**术语先定义后使用**。新术语首次出现即定义，此后全篇只用这一个名字；术语密集的文档另维护术语表。

**删冗余前导**。「需要注意的是」「值得注意的是」不承载信息，直接从正文开始。

## 3 结构组织

**总览先行**。开篇让读者建立全局观：这篇文档是什么、写给谁、覆盖什么、各部分去哪找。篇幅超过一屏的文档，开篇给导航（目录或任务入口表）。

**面向任务组织**。按读者要完成的事组织内容，不按系统内部结构组织——写「如何新增共享定义」，不写「definitions 包介绍」。

**平行结构**。同类条目同构呈现：同形态的标题、同顺序的字段、同格式的示例。并列的项必须同级，子项不混入父级清单。

**标题即内容**。标题直接陈述该节讲什么；「其他」「杂项」「简介」类不承载信息的标题禁止使用。

**层级只表达包含**。标题层级用于内容的包含关系，不用于强调；跳级即结构错误。

## 4 格式规范

**代码标识等宽**。模块路径、函数、常量、环境变量、CLI 参数一律用等宽标记，保留英文原文，不翻译。

**中西文间距**。中文与英文、数字之间加一个半角空格。

**标点**。正文用全角中文标点；等宽代码与英文引述内的标点随原文。

**数量与单位**。数量用阿拉伯数字，单位紧跟数值（30 秒、50MB）；写上下限时写明含不含边界（「不超过」「小于」）。

**交叉引用带锚点**。「见 S1」「见 D1 表」指向确定的编号或章节；「见上文」「如前所述」禁止。

**表格用于枚举与对照**。可逐行对照的信息用表格；叙事与流程用正文、列表或图示。

**列表项同构**。同一列表的每一项用同一词性开头——全部名词短语，或全部动词短语。

## 5 规范性文档专项

**条目模板**。规范性文档的规则条目按统一模板撰写：

> **意图**：一句话，本条为什么存在。
> **规则**：条目正文。
> **例外**：不受本条约束的场合。
> **机器执行**：守护本条的测试锚点。
> **参见**：关联条款。
>
> 例外、机器执行与参见行，如无则省略。

**编号稳定**。条目只增补、不改号、不复用；废弃条目保留编号并标注废弃，不删除。

**快照外移**。随代码漂移的清单（导入白名单、路径清单、注册名单）置于附录，正文声明权威源所在；正文只留规则与登记流程。

**情态词表**。须＝强制；禁止＝强制不做；仅允许＝封闭集合；应当＝无充分理由须遵守；可以＝可选。与 repo-layout.md 元信息表同表，不得另造同义词。

**变更记录**。文档末尾维护变更记录，每个版本一行：版本、日期、变更要点。

## 6 交付前自查

写完一篇文档，逐条过：

1. 只读各章首句，能否拼出全文脉络？（意图先行）
2. 有没有任何一个概念用了两个名字？（一致）
3. 逐句自问「删掉这句损失什么」——答不上来的句子删掉。（简洁）
4. 并列的项是否全部同级、同构？（平行结构）
5. 每个交叉引用是否指向确定的编号？（锚点）
6. 规范性文档：每条规则条目能否按模板逐字段对上？（条目模板）

## 正误对照

| 规则     | 反例                             | 正例                                                        |
| -------- | -------------------------------- | ----------------------------------------------------------- |
| 意图先行 | 「D1 跨包边表：」                | 「D1 跨包边：跨包导入仅允许下表方向，防依赖随意生长成网。」 |
| 现在时态 | 「配置后将可以支持」             | 「配置后支持」                                              |
| 具体用词 | 「重试适当的次数」               | 「最多重试 3 次」                                           |
| 快照外移 | 「目前包根共有六个域包」         | 「域包封闭集合见 S1」                                       |
| 锚点引用 | 「见上文所述」                   | 「见 S2」                                                   |
| 列表同构 | 「新增工具」与「工具的注册」混杂 | 「新增工具」「注册资源」「挂载路由」                        |
